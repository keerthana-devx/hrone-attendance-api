# DECISIONS.md

1. **Indexes.** Five indexes were created at startup. A unique index on `employees.emp_code` enforces one employee per code and supports fast lookups. A unique compound index on `attendance_logs(emp_code, date)` enforces one record per employee per day and supports punch-in duplicate detection. A compound index on `attendance_logs(date DESC, emp_code ASC)` supports the attendance list sort. A compound index on `attendance_logs(emp_code, punch_in)` supports the punch-out query that finds the most recent punch-in at or before a given instant. A compound index on `attendance_logs(emp_code, date, status)` supports monthly analytics filters. An index on `employees.department` supports department filtering. Considered but rejected: a separate index on `attendance_logs.status` alone — the compound indexes already cover status as a suffix, and a standalone status index would be low-selectivity and rarely the best plan.

2. **Punch-in race.** Both requests reach `insert_one` at nearly the same instant. MongoDB processes them serially at the collection level. The first insert succeeds and creates the document. The second insert hits the unique compound index on `(emp_code, date)` and raises `DuplicateKeyError`. The application catches that error and returns HTTP 409. No check-then-insert sequence is used, so there is no window where both can succeed.

3. **Ties at the leaderboard cutoff.** If two employees share the same `total_late_minutes` and that value falls at rank equal to `limit`, both are returned. The ranking loop assigns the same rank to tied employees and skips the next rank (standard competition ranking: 1, 2, 2, 4). The filter `rank <= limit` then includes every tied employee at that rank, so the response may contain more rows than `limit`.

4. **Headcount with zero logs.** The department summary starts its aggregation from the `employees` collection (filtered by `joined_on <= last day of month`), then groups by department to get `emp_codes`. Attendance logs are fetched separately and joined in Python. Employees with no logs simply contribute zero to every metric but are still counted in `headcount`.

6. **`$densify` in department trend.** The `/analytics/departments/{department}/trend` endpoint uses MongoDB `$densify` (available since MongoDB 5.1; confirmed 8.3.1 in this environment) to guarantee one document per calendar date in the requested range. Attendance logs are grouped by a UTC-midnight datetime field derived from the ISO date string via `$dateFromString`, then `$densify` fills gaps with zero-valued documents before the Python layer computes headcount, attendance rate, and 7-day moving average. This satisfies the assignment requirement explicitly calling for `$densify` and eliminates the previous Python-loop approach that fetched all logs into memory.

5. **One change for 100x data.** Move the department summary and trend computations fully into MongoDB aggregation pipelines with `$lookup` and `$group`, eliminating the Python-side loop over employee codes and log records. At 100x scale the current approach of fetching all logs into Python memory becomes a bottleneck; a pure server-side pipeline with proper indexes would keep memory usage constant.
